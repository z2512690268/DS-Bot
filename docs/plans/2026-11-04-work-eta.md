# 派活的预计时长与偏差监督

- 日期：2026-11-04
- 相关：`feat/work-eta`（基于 `feat/work-state-report`）

## 为什么

派活是 DS Bot 的主要工作方式，但一件活要多久、有没有跑偏，之前没有任何时间口径：
只有 30 分钟的停滞租约，等到那时才发现已经太晚。用户要求「派活要预测多久，并且有东西
盯着，进度不对就立刻分析调整」，同时明确**不要把偏差报给用户让他决定**——用户只能审核
一句，真正要推进的是主 Bot。

横向换人没有意义：团队里大部分 Bot 跑同一个模型，换个人等于同一个脑子再想一遍。所以
卡住时走的是**纵向升档**：先升思考强度，再升模型，最后才是新开一个高配 Bot。

## 已定的行为

### 预计时长（ETA）

- `message_bot` 有可选参数 `eta`：分钟数或一句话（`20`、`20 minutes`、`半小时`、`几小时`）。
  `parseEta` 解析成 `{ text, minutes }`，数字按分钟，带单位按单位换算，中文数字与「半 /
  几 / 数」按近似值处理并标 `approximate`。解析不出数字时视为未估时，派活照常进行。
- ETA 存在 work 上（`work.eta`），随 `state.json` 保存；主进程重启后仍在。
- `create_bot` 也有 `eta`：创建 Bot 不开 work，所以这个估计存在 Bot 记录上
  （`state.bots[id].eta`），只用于展示，不参与监督。

### 偏差监督

- 复用停滞扫描的 60 秒定时器（`sweepEta`），只比时间：`已用 / 预计`。
- **80%**：给派活方一条提示（role `eta`），写清预计多少、已过多少、下一步建议。
- **150%**：再来一条（role `eta-late`），措辞升级。
- **同一件活最多两条**；标记在 `work.eta.reminded`（落盘），所以重启后不会重发。
- 活报 `ready` / `blocked` / `failed` / `dropped`、或有最终报告后不再提醒；`progress`
  报告不解除（时间口径不看内容）。
- 提示只投递给派活方（`work.from`）的私聊队列：**不进 needsYou、不生成提问卡**。
- 提示里直接给建议动作，主 Bot 一次调用就能执行：
  - 第一档：`update_bot bot "X" effort "<更高档>" temporary true`（档位取自
    `list_bot_models` 里该模型支持的 levels，找当前档的下一个）；
  - 第二档：`update_bot ... model "<更强模型>" temporary true`；
  - 第三档：`create_bot` 一个专用高配 Bot，带失败诊断（试过什么、报什么错、排除了什么），
    做完把结论交回原 Bot。

### 临时升档与恢复

- `update_bot` 新增 `temporary`：仅在「该 Bot 手上有一件活正处于偏差提醒中」时可用，否则
  拒绝；必须同时带 `model` 或 `effort`。
- 升档前的 `model` / `effort` 记在 work 的 `escalation` 上；工作结束（close/drop）时自动
  恢复**如果**当前值仍是升上去的值（中间被改过就以新的为准），并记 `restore` /
  `restore-skipped`。
- 不带 `temporary` 的升档也会被识别（同一个 pending 提醒 + 改了 model/effort），记为
  `temporary: false`，审计注明「因卡住升档，但不恢复」——对应「要么改回去，要么写明」。

### 横向转派

- 偏差提醒存在期间，主 Bot 用 `message_bot` 把活交给**另一个** Bot，审计记为
  `kind: 'hand'`、`ladder: 'horizontal'`、`nonDefault: true`。这不是默认手段；只有原 Bot
  上下文被污染或太长时才用，理由由主 Bot 自己写在消息里。
- `stop_bot` 记 `stop`，`keep_working` 记 `self`，`create_bot` 记 `new-bot`。

### 审计与面板

- `state.etaAudit`（最多 200 条，只读接口 `rt.etaAudit()`）记录每次提醒
  （`due` / `late`，带预计与已用）、每次升档（`effort` / `model`，带原值与新值与
  `temporary`）、每次恢复（`restore` / `restore-skipped`）和每次处置。
- 关闭的 work 在 `workLog` 里保留 `eta.minutes`、`eta.reminded`、`eta.escalation` 与最终
  `final`，能回答「这件活估了多少、提醒过几次、升过档、最后怎么结束」。
- 面板在「需要你」区块里有一行（每件在跑的活一行）：`预计 X · 已用 Y`，超过 80% 标黄、
  超过 150% 标红；升过档的加「已升档」。只展示，不给按钮、不要求用户操作。

## 不做什么

- 不预测工作内容，也不调模型来估时长：只用派活方给的分钟数和时钟。
- 不因超时直接停 Bot 或改派：动作由主 Bot 决定，机制只负责提醒和留痕。
- 不给用户发提问卡，不把偏差放进「需要你」。
- 不做 ETA 的事后修改（一件活的预计时长在派活时定下）。

## 已知限制

- 待处理的偏差提醒存在内存里（`etaPending`），只在本次运行有效；重启后提醒仍在 work
  历史和 `etaAudit` 里，但主 Bot 的后续动作不再能对上那一条提醒。
- 「处置」按动作类型推断：同一会话同时有多条提醒时，`stop_bot` 按目标 Bot 匹配，
  `message_bot` 取最近一条；无法百分之百保证对上是哪一件活。
- 恢复是尽力而为：`update_bot` 失败时只记日志和审计，不重试。
- 已经有最终报告的活不再提醒，即使之后又停住——那是停滞租约（`work-stall`）负责的范围。

## 变更

- 2026-11-04：初版。ETA、80%/150% 提醒、升档阶梯（effort → model → 专用 Bot）、临时升档
  与恢复、审计和面板一行。
