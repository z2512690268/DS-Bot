# 派活的报告与等待状态

- 日期：2026-11-02
- 相关：延续 [Bot 之间派活](2026-10-16-bot-handoffs.md)；参考 dsh-superagent 的调度设计

## 为什么

派活树解决了「结果自己交回」，但结果只有一段自由文本。上游 Bot 要判断下一步，必须读全文才能分出四件不同的事：

- 做完了，可以验收；
- 做不下去，要用户决定或补资源；
- 根本做不了；
- 其实没什么要做的。

上游再把这四种转述给用户，转述一次就掉一次信息；用户问「到哪了」，界面上只有 Bot 级状态（在干活 / 在等别的 Bot），看不到一件活具体在等什么、等了多久。

dsh-superagent 的做法是把这两件事都变成字段：结果带 `state`（progress / ready / blocked / failed / dropped），状态由事实推导而不是由模型自述，进度默认安静。这里只取这两个做法，**不引入它的工单对象**：活仍然是消息，仍然在派活树里。

## 已定的行为

### `report` 工具

- Bot 在回答别的 Bot 的活时，可以调 `report`：
  - `state`：`progress`、`ready`、`blocked`、`failed`、`dropped`，必填；
  - `summary`：一句话，最多 500 字，用用户的语言；
  - `human_action`：用户必须做或决定的一件事，写成一句问句，最多 500 字，只在 `blocked` / `failed` 时有意义；
  - `human_options`：2–4 个用户可以点的答案，同一语言，只在有 `human_action` 时有意义。
- `progress` 不关闭活，也不进交给上游的回答，只记在这件活上，供 `list_bots` 读取。
- 其余四个状态跟着回答一起交给上游，写在这件活的结果**上面**：
  ```
  [reported blocked: 读不到那份文件]
  请给这份文档的读取权限

  （Bot 的正文）
  ```
- 一个回合结束时没有调过 `report`，按 `ready` 理解。这与原来的行为一致，不改现有 Bot 的习惯。
- 不在回答任何活的回合里调 `report`：返回一句「没什么可报告」，不算失败。
- `state` 不在五者之内：拒绝，并说明可选值。
- `summary` 与 `human_action` 去掉多余空白、截到 500 字。

### 等待状态

- 一件活的状态由事实推导，从上往下取第一条：

  | 状态 | 条件 |
  |---|---|
  | `person/answer` | 这件活上有一个用户还没回答的问题 |
  | `person/blocked` | 认领它的 Bot 报了 `blocked` |
  | `person/failed` | 认领它的 Bot 报了 `failed` |
  | `person/review` | 认领它的 Bot 报了 `ready` |
  | `working` | 其他 |

- 推导是纯函数（`src/host/work-state.js`），模型不能直接写状态。
- `statusOf` 里「在等 X 交回」现在带等了多久，以及对方报上来的 `blocked` / `failed` 摘要：
  `waiting for 12 min for Tester to hand back work; it reported blocked: 需要一份凭据, for Chief`。
- 因此 `list_bots` 和 `message_bot` 的结果都会带上这两项，不需要新工具。

### 需要用户做的事，变成一张卡

- 一个汇报带 `human_action`（且状态不是 `ready` 或 `dropped`）时，交回回答的那一刻，插件在**派活的 Bot 的私聊**里写一张提问卡：问题就是 `human_action`，说明行是 `<做活的 Bot>: <summary>`；带 `human_options` 时它们是卡片上可以点的答案，同时始终可以自由输入。
- 因此 `human_action` 必须是**一句问句，用用户的语言**写：它是卡片的标题，不是命令，也不是标签。`summary` 同一语言。这条写在工具说明和团队规则里，因为插件不翻译。
- 谁问的活，就在谁那里问：答案是给用户的，卡片就出现在要转达它的那个 Bot 面前。
- 那个 Bot 已经有一张没答的卡时不覆盖，用户正在回答别的问题。
- 用户在卡上作答后，答案**直接**发回做活的 Bot：插件以"派活的 Bot"为发件人开一件新的活，内容是「用户回答了你问的『<问题>』：<答案>」。派活的 Bot 不用花一个回合转述；做活的 Bot 交回结果时，派活的 Bot 照常拿回结果。

### 停滞的工作

- 一件活 30 分钟没有新汇报（`progress` 也算一次汇报）时，插件把它标成 `blocked`，摘要写 `no progress for N min`，原因记 `no_progress`，时间记作标记的时刻。
- 标记的同时做出动作，策略是常量（`work-state.js` 的 `LEASE_POLICY`），插件配置可覆盖：
  - `leaseAction: 'notify'`（默认）：给派活的 Bot 一条 `stalled` 输入，它下一次回合读到「这件活停滞了」，可以自己做、转给别人或告诉用户。这条输入不要求回复，也不唤醒不在跑的 Bot。
  - `leaseAction: 'redispatch'`：在通知之外，把同一件活交回做活的 Bot。重派用 `request_id`（以活为名）保证幂等：同一次扫描、重复扫描、重启后都不会执行第二次。
  - 停滞只动作一次：标记留在活上，`report` 一来就清掉，下一次沉默才算新的一次停滞。
- 每分钟查一次。已经报过结果的活不再标，`progress` 把计时清零。
- **等待本身就是进展**：做活的 Bot 有存活的后台 job 时，这段沉默不算停滞。判定用一条政策常量（`work-state.js` 的 `JOB_EXPECTED_MS` / `JOB_GRACE_MS`）：
  - job 还在它预期的时长内（默认 30 分钟）：豁免，不标停滞；
  - 超过预期时长后，只有该 job 还在写东西（输出总量在涨，或有 progress 行）才算进展；
  - 超过预期时长的 2 倍（默认 60 分钟）且一直没输出：不再豁免，照常标停滞，并在摘要里写清 `a background job has produced no output for N min`，让派活方知道是"卡在 job 上"而不是"没人管"。
  - job 一 settled，豁免自然消失，回到正常判定；不需要额外上报。
- 这解决的是真实误报：Bot 挂着一个本来就该等几小时的集群实验，30 分钟就被标 `no progress`，用户只能自己 ssh 去核 GPU。
- 已经停滞、又已被用户 dismiss 的活，下一次扫描把它从 `works()` 收掉并留一行 `workLog`；还挂着子活的先不动。扫描幂等，收掉之后不会再出现。

### 租约

- 一件活开出来就带上 `lease`（什么时候、交到谁手上），每次 `report`（含 `progress`）把它向后推。停滞判定读的是它，所以「还在干」和「没人管」能分开。
- 默认 30 分钟；`workDeadlineMinutes` 可以改。

### 准入

- 每件活记 `authority`：`asked`（用户要的）、`delegated`（别的 Bot 派的）、`proposed`（Bot 自己想做的）。
- 团队设置 `proactive: off | observe | auto`（默认 `observe`）决定 Bot 自发的活怎么办：
  - `off`：只能做 `asked` / `delegated`，发起的请求被拒绝，什么也不记。
  - `observe`：请求**只记录不推进**，记成一件 `proposed` 的活（没有租约，不会被判停滞），出现在 `needsYou()` 的「我本来会做」一组里，工具结果告诉 Bot 不要重发。用户可以**批准**（`approve-proposal`）：这条提议变成真的派活，请求名以提议为名，重启/重复批准都不会发第二次；也可以忽略。
  - `auto`：照常发送。
  - `propose` 工具：Bot 在**群里没被点名**的回合里，把看到的具体活记成一条提议（标题 + 一句理由），不执行、不发给任何 Bot，进「我本来会做」；每回合最多一条。私聊、被点名的回合、由管理员主持的回合都不生效。
- 什么算「Bot 自己发起」由回合推导：它在回答哪件活就随那件活；用户的私聊、用户点名、别的 Bot 派活都是 `asked` / `delegated`；群聊里由管理员主持的那一轮也是 asked，没被点名的成员在轮次里顺带发起的才算 `proposed`。
- 引用、转发、文件、网页都是数据，不构成请求。

### 度量

- 一件活关掉时，在 `state.workLog`（最多 500 条）留一行：`final`（最终状态）、`turns`（回合数）、`ms`（开始到结束的时长）、`authority`、`results`、`history`。
- `turns` 由回答这件活的回合累加。
- `rt.workStats()` 只读地给出汇总（`closed`、`open`、`byFinal`、`turns`、`avgMs`），以及最近 24 小时的 `day`（关闭数、中位时长、停滞数、投递/回答失败数）；`state` 负载里的 `workStats` 就是它。
- 面板把 `day` 折成一行安静摘要，只有当天有事时才出现。
- 不做仪表盘。

### 收件箱

- `needsYou()` 的每一条都带 `key`（`answer:<questionId>` 或 `<kind>:<workId>`），面板据此一次处理多条。
- `needs-dismiss` 接口接受一组 key：忽略的 `proposed` 活直接丢掉；已停滞的 `blocked` 活也真正收掉（不留残留，但它还挂着子的活时不收）；其余 `blocked` / `review` 的活只是从列表里隐藏，状态再变（`since` 晚于忽略时刻）就重新出现。
- `approve-proposal` 接口把一条 `proposed` 的活变成真派活：记录本身变成那条请求（答案回到同一件活），原文整条保留（超过内联上限的不能批准，只能让 Bot 重提），发一次、幂等。
- 客户端可以全部展开、逐条作答、逐条或全部忽略。

### 面板的健康与历史

- `rt.workHealth()`：停滞的活数、最近一小时的投递失败数、回答失败数；全为 0 时面板不占位。停滞数与 `needsYou()` 用同一套可见性规则，被用户 dismiss 的停滞不再计入。
- 面板另有一行 24 小时摘要（关闭数、中位时长、停滞、失败），安静的日子不出现。
- `rt.workHistory(id)`：一件活从创建到结束的时间线（`created` / `proposed` / 各次 `report` / `stalled` / `closed`），开着的活读记录，关掉的活读 `workLog`；`needsYou()` 的工作条目也带上它，面板在行内展开。

### 并发

- 任何 Bot 正在跑的回合数达到 8 时，Bot 之间的消息不再插进对方的当前回合，改为等它下一个回合。用户自己的消息不受这条限制：它总是直接开始一个回合。

## 不做什么

- 不做看板式的任务对象：活仍然是消息，派活树的结构不变。
- 不新增顶层实体，也不给活加 id 之外的标识。
- 不做看板式面板：聚合数据由插件的 `needsYou()` / `workStats()` / `workHealth()` / `workHistory()` 提供，界面只在侧栏区块里用。
- 不把状态写进系统提示（缓存要稳定）。
- 不让插件自己把用户的回答转发给做活的 Bot：那要伪造一条请求，还要决定谁是发件人；由派活的 Bot 转达，一步模型调用换取它可以改写措辞、补充上下文。

## 已知限制

- `progress` 只记在 `state.json` 的活上，界面还看不到它。
- `dropped` 仍然会走一条回答交给上游，否则上游会一直等它。dsh-superagent 那边可以静默结束，是因为它有自己的工单结束事件；DS Bot 没有这个通道。
- `person/review` 只在「报了 ready、回合还没结束」的窗口里出现，通常极短。
- 报告是 Bot 的判断，不是证据；`ready` 依然不等于「已验收」。
- 提问卡的答案要经过派活的 Bot 转发一次，那一步是模型调用；它漏转，答案就到不了做活的 Bot。
- 停滞只通知派活的 Bot 一次（下一次回合读到），它不打开对话就不会因此开口。
- 重派只重派一次（以活为名），第二次停滞只通知不重派。
- 观察模式记录的是「本来会发的请求」，不含 `request_id` 语义的重放；重复的同一条请求只记一次。
- 度量只记关掉的活；开着的活只出现在 `workStats().open`。
