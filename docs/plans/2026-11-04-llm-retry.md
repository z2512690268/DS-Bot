# 模型服务抖动时自动重试

- 日期：2026-11-04
- 相关：`feat/llm-retry`（基于 `feat/work-state-report`）

## 为什么

今天至少四次因为模型服务过载 / 传输失败（`TRANSPORT`、pi-ai 的
`PI_AI_ERROR: servers overloaded`）直接丢掉回合结果：一次请求失败，整件活就没了，
只能重来。用户要求「多重试几次」。

DSH 自带 `@deepseek-ai/dsh-llm-retry`，但它的默认重试集合是
`EMPTY_RESPONSE / RATE_LIMIT / SERVER / TIMEOUT / TRANSPORT`；pi-ai 把
「servers overloaded」归成 `PI_AI_ERROR`，不在这个集合里，所以这类失败并不会被重试。

## 已定的行为

- DS Bot 在 `agent/request-error` 这个公开扩展点上再加一层重试，和 DSH 自己的
  重试执行器用同一个契约：返回 `{ kind: 'retry' }` 就在**同一个回合**里重跑失败的那一步。
- **先让下游决定**：先调用 `next()`；上下文管家、provider 自己的重试策略、主 Bot 的恢复
  只要给出了决定，就用它的，不重复计数，也不覆盖。下游没有决定时这一层才动手。
- **可重试**：`TRANSPORT`、`SERVER`、`RATE_LIMIT`、`TIMEOUT`、`EMPTY_RESPONSE`，以及
  正文含 overload / capacity / too many requests / service unavailable / try again / busy
  的 `PI_AI_ERROR`。
- **不重试**：`AUTH`（401/403）、`INVALID_CREDENTIAL`、`MISSING_CREDENTIAL`、`QUOTA`、
  `ACCOUNT_QUOTA`、`INVALID_REQUEST`，以及 `CONTEXT_WINDOW_EXCEEDED`、`ABORTED`、
  `NO_ADAPTER`、`HOSTED_ENGINE_ROUTE`。前一组会**立即**把工作标 failed 并告诉派活方，
  附上 provider 的错误码与消息；后一组交给已有的机制（换段/中止等）。
- **退避**：默认 3 次，基数 5 秒，序列 5s / 15s / 45s（1x、3x、9x），每次 ±10% 抖动，
  避免一队 Bot 同时回来。次数与基数用 `llmRetryAttempts`、`llmRetryBaseSeconds` 配置；
  `llmRetryAttempts: 0` 关掉这一层。
- **每次失败按「回合 + 步骤」计数**：同一个步骤被重跑，所以同一个预算；重试成功后进入下一步，
  预算是新的。回合结束清空。
- **等待可中断**：重试等待期间用户叫停（`signal` abort），立即放弃，不消耗这次预算。
- **重试用尽**：本次仍返回失败，回合按 DSH 的方式结束；同时把该 Bot 手上未终态的 work 标成
  `failed`（摘要带 `after N retries (CODE: message)`），打 `halted` 让续跑不再踢它，
  并给派活方一条 `[A work you handed on to X could not be answered]`（写明错误与可选动作）。
- **不丢工作、不重跑工具**：重试发生在同一个未结束的回合里、同一份持久历史上，已经完成的
  工具调用不会重跑；回合在整个等待期间保持「进行中」，所以续跑看门狗看到的是正在干活，
  不会注入续跑提示。
- **可观测**：
  - 诊断日志每次一条（`source: retry`）：哪次、第几轮/最多几轮、错误码、退避毫秒、最终失败；
  - `state.llmRetries`（最多 200 条，只读 `rt.llmRetryAudit()` / `rt.llmRetryView()`）；
  - 面板健康线：近一小时「重试 N 次 · 重试后仍失败 M 次」，都为 0 时保持安静。

## 不做什么

- 不修改 DSH：只用 `agent/request-error` 扩展点，与自带重试执行器共存。
- 不无限重试（那是 provider 的 `mode: always` 策略），默认 3 次。
- 不重试鉴权、额度、非法请求、上下文超限与中止。
- 不因为重试而改动 work 的等待状态或消息历史：重试对模型与用户都不可见。

## 已知限制

- 重试依赖 DSH agent loop「重跑失败步骤」的语义；`ctx.llm.stream()` 的直接调用不经过这里。
- 如果 provider 自己配置了 `always` 策略，DSH 的重试会先跑完，这一层只在下游放弃后补 3 次。
- 每次重试都是一次计费请求，默认 3 次意味着最坏情况下一轮失败要花 4 次请求。
- 一次模型故障覆盖不了「provider 整体不可用」：3 次都失败后仍然要靠人决定下一步。
